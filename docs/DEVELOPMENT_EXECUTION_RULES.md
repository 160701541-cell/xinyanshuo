# 《苍岚》研发交付不可违背规则

> 2026-10-16 用户反复确认。后续所有协作会话先阅读此文件，再开展开发。

1. **唯一允许开发和发布的 GitHub 仓库**：公开仓库 `160701541-cell/xinyanshuo` 的 `main`。不得继续操作私人旧仓库，也不得在另一处建立替代工程作为交付。
2. **唯一交付目标**：让用户手机上**已经安装的《苍岚》**获得可见、可运行的新场景/素材。静态网页、ZIP、构图演示、独立测试APK均不能冒充正式游戏更新。
3. **优先使用现有热更新**：按原手机APK实际协议、版本兼容区间、RSA公钥和私密签名能力构建真正可被客户端接受的 `.pck`，在GitHub/Pages发布完整资源包和经签名的更新清单。签名能力不足或兼容性无法核实必须如实标记 BLOCKED，绝不能伪造签名、更新状态或随意改 `android-preview/latest.json`。
4. **必须更换APK时**：只通过公开仓库构建，并核验与手机已有正式APK**应用ID、签名证书、versionCode**一致且可覆盖安装；不是另一个包名、调试签名或无法保留原存档的独立APK。
5. **素材必须真实拼进游戏**：把已生成的青楼、草房小院、宗门大殿、客栈、城门和石砖道路作为独立源图审核，导入游戏资源路径、布置场景，并验证资源实际可见。无缝道路必须做接缝验证。旧低质量图集不是替代品。
6. **真实QA和证据**：逐项记录提交SHA、引擎运行、显示效果、APK/PCK生成、签名校验、远端HTTP可访问、客户端可更新测试及手机实机状态。绝不以源码提交或CI触发代替通过，更不能虚报“已经更新进游戏”。
7. **官网展示和开发日志**：完成的图片及迭代结果展示到已有官网，更新原仓库工作日志，说明本次真实完成与阻塞。
8. **用户无需重复指导**：助手承担制作人和研发负责人的职责，优先解决阻塞并交付手机可测更新，不再反复询问已确定的路线。

## 2026-10-16 用户修订：稳定任务允许并行，不是一律单线程

此前“每次只做一个任务”针对的是**长时间卡顿、无效构建、重复消费额度和相互阻塞**，并不是永久禁止多任务。

- **可并行**：WorldX/Kolors 素材工厂在生成、上传、质量门禁已验证稳定且成本可控时，可与独立的建筑拆分、Godot 接入、原APK兼容性修复、文档/官网维护并行；不同批次必须有可追踪的运行编号与产物，分开报告状态。
- **必须串行**：同一文件、同一 Git 分支写入的互斥修改、共享状态、同一版本 APK 的签名发布与发布门禁；先解决互相依赖和写入竞争后再执行。
- **停止条件**：出现连续失败、长时间无输出、API 额度异常消耗、CI 任务堆积、构建结果相互覆盖时，立即暂停出问题的任务链，定位修复；不影响其他已验证的独立任务。
- **批次控制**：生成任务合理设定并发上限和单次费用/调用次数，QA 未通过的候选不能自动混入正式素材库；不要在没有稳定画风控制时无限生成。
- **交付原则**：后台能并行就并行，但每条任务都必须有真实产物和 QA 证据；不把“不会卡”的判断等同于已经解决产线瓶颈。

用户希望助手自主调度独立稳定的工作流，**而不是要求用户逐项点击或重复发送“下一步”**。

## 2026-10-16 实际执行节奏：禁止高频轮询

- 在同一段主动研发会话中，同一 GitHub Actions 构建的运行状态**最多每120秒查询一次**；不得连续“查状态→等待→再查状态”空耗时间、上下文或请求额度。
- 发起 CI 后立刻在间隔时间推进**不依赖该构建结果**的工作，例如实际代码、美术分层工具、游戏交互、测试用例与开发记录。对不同工作流统一批量查询，能不查就不查。
- 仅在构建结果将影响当前提交的质量决策时才查询；如果任务已产出可用证据，直接报告已验证的状态，不用为了刷“绿色”连续轮询。
- 若有依赖，采用 GitHub Actions 自身的依赖/事件触发机制，而非靠聊天工具每几秒刷一次。不要将“单次对话内少轮询”误说成可以永久后台运行。
- 用户允许稳定独立任务并行，限制的是无效等待、竞争冲突及失控重复生成。不得让用户手动代替助手开发。
