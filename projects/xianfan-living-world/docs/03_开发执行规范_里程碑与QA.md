# 独立项目开发执行规范、阶段规划及质量验收 V0.1

> 本文是未来开发人员和AI协作的执行约束。**当前只完成需求与技术设计，未创建游戏程序或完成运行验收。**

## 1. 开发总策略

目标不是第一天建造整个仙界，而是以一个实际可玩的县为核心，保证后续每增加一个玩法都扩大同一个世界，而不是增加一套孤立的文字按钮。

**必须遵守的顺序**：规则数据最小闭环 → 可视、可操作的移动端原型 → NPC真实日程与交互 → 跨系统因果链 → 修仙与世俗共生 → 长期世界历史 → 扩大规模。

任何「成功」声明分为：`DESIGNED`（已设计）、`CODED`（有代码）、`UNIT_TESTED`（单测）、`INTEGRATION_TESTED`（联调）、`DEVICE_TESTED`（手机实测）、`RELEASED`（实际可安装/使用）。不可越级标注。

## 2. 代码及资产边界

- 独立新项目/独立仓库；不得写入已有两款游戏正式分支。
- 先进行许可核验：可借鉴MUD的房间关系、世界组织思想，但不得擅自复刻原游戏人物、地图文本、原创任务或侵权素材。
- 核心规则与展示层分离；API出入参类型化，绝不允许UI直接修改经济余额或人物爱情状态。
- 一个稳定的实体ID贯穿出生、户籍、位置、商铺、婚姻、死亡、继承与历史。
- 事务具备原子性与幂等处理，消除重复扣款、复制物品和人凭空复活。
- 新增一个系统必须明确：实体字段、输入资源、输出资源、事件、权限、保存、AI可见信息、UI入口和测试。
- 设计与需求使用中文文档，代码命名和接口可以统一采用英文标准，禁止同义重复字段。

## 3. 原型技术路线（待验证的建议，而非架构承诺）

建议移动端优先、离线优先。客户端可选TypeScript + Svelte，使用响应式组件展示场景、地图、行动、人物与纪事；计算核心先使用可独立运行的TypeScript服务/Worker模块，避免UI阻塞；持久化依平台选择SQLite/IndexedDB等经实测的技术。后续若出现计算瓶颈，再根据基准分析抽取耗时模块到Rust/WASM或原生代码。Android可在Web原型验收后评估Capacitor封装，但不把「Web能打开」当成APK已通过。

**重要取舍**：在真实原型前不预先绑定FluffOS、不预设多人联网、不要求本地大模型作为所有NPC的CPU核心。NPC先由确定性规则与有限理性算法自主行动；文本模型仅用于语言自然化，支持关闭。

## 4. 里程碑与每轮交付门槛

| 阶段 | 必交付的可运行结果 | 验收焦点 |
|---|---|---|
| P0 / 世界骨架 | 独立工程、世界时钟、存档、人物ID、房间/区域地图、手机导航UI | 多次进出同一房屋位置和状态不丢；存档复现 |
| P1 / 活县城 | 1000人身份档案、数十精细NPC、家庭/职业/作息、两村一县、基础农商经济 | 行业真实生产消费与商铺营业；非玩家NPC跨房间移动 |
| P2 / 人生社会 | 相识、关系图、婚制、家庭、拒绝、分离、死亡、继承、关系回忆 | 没有「送礼刷分结婚」；双方有独立行为；同意门禁有效 |
| P3 / 官府与修仙 | 县官权限、税收/赈灾、宗门门规、灵根修炼、御剑跨区旅行 | 同一库存/人口/历史；飞行可遇到实际商队 |
| P4 / 一局的人生史 | 历史记录、地方志、家谱、归乡、不同种子的多局演化 | 闭关多年NPC仍有完整演化；历史不凭空杜撰 |
| P5 / 世界扩容 | 多城、多势力、自动调度、模拟精度切换、性能优化 | 规模增长后稳定、守恒且可观察一致 |

阶段优先级不是每阶段锁死玩法。例如P0就要保留修士位置和移动模式的接口，P1已经存在至少少量能行动的修士；不要把修仙当最后才贴上的独立模块。

## 5. 第一版验收故事（测试用例，不是固定主线）

**测试一 / 同一座城**：角色从家中走到粮行，买米后钱包减少、粮行库存减少；返回家中，米在家庭或人物库存中；营业打烊后掌柜返回住所。

**测试二 / 失去和遇见**：两名NPC因赶集自然相识；玩家几天后再来，可查证两人后来是否联络；一人可以拒绝另一个人，不能用礼物强制逆转。

**测试三 / 世俗权力**：玩家成为有权限的县官后发放赈济；县库减少、粮仓出库、实际家庭获粮；如果粮食不足，不允许只显示漂亮的「赈济成功」。

**测试四 / 仙凡一体**：玩家御剑到宗门，在途中看见运粮车队；山上闭关十年，期间原县发生收成、婚育、升迁、死亡；返回后可通过可信来源追查部分历史。

**测试五 / 每局差异**：两局只改变某场降雨时机，观察交易路线、成本与家庭选择是否发生实际变化；历史必须标明因果，不用硬编码「第二局成为大侠」。

## 6. 质量体系：不因为是文字游戏就降低标准

### 6.1 正确性

- 状态唯一：一个NPC不可同时住在两个房间（除明确设定的远程行为）；一个物品不可在两处被全额拥有。
- 资源守恒：经济交易货物、金钱和税费按事务平账；自然生长、采矿、铸币等作为有说明的外源事件。
- 时间因果：不能在亡者死亡时间后由其签署公文；不能在收徒考试结束后回写已录取人物。
- 权限正确：县令不能越级颁布皇帝诏书；宗门弟子不能任意打开护山大阵。
- 历史一致：同一事实在事件记录、人物履历、地方志引用一致；允许角色说谎或记错，但必须体现为知识差异。
- 关系自主：单向爱慕不等于恋爱；胁迫不等于同意；收养、监护、债务不得兑换性亲密。

### 6.2 UI与易用性

- 游戏主界面不堆叠全部菜单；相同信息在不同页面用同一组件呈现。
- 标题、正文、注释、风险通知有清晰层级；移动端字体可调、触控区域合理、字号放大不遮挡。
- 地图默认展示当前位置、可到达目标、行动成本；历史和探索信息支持筛选。
- 典型县城内从家到商铺不超过数次操作；日常重复路程可自动导航。
- 日志默认聚合重复事件；重大事故提醒可暂停加速/旅行；玩家可以查询完整细节。
- 只显示玩家应知信息；未知NPC隐私不得从人物面板自动泄露。

### 6.3 内容质量与价值边界

- 不以低俗描写或伤害取代复杂情感；涉强迫、剥削与未成年人相关剧情严格遵守年龄与内容限制。
- 被救助的人有自主生活能力，不因受恩被系统强制报答或成为伴侣。
- 制度背景可存在压迫、不公与冲突，但玩家及NPC都能有真实反应；不以作者观点强迫NPC选择。
- 允许普通平凡生活，避免用连环离奇死亡制造廉价波澜。

### 6.4 稳定性与移动端

- 模拟引擎与UI线程解耦；大段补算必须可暂停并反馈进度。
- 存档支持版本迁移、定期快照、异常回滚；关闭时不损坏长期世界。
- Android运行须实机测试；记CPU时间、峰值内存、冷启动、导航流畅度、存档读写大小及电池负担。
- 性能指标先作为测试计划，不在没有设备数据时写虚假的 FPS 或百万NPC承诺。

## 7. 属性设计防止数值游戏化

不公开NPC所有真实情感数字；但后端状态必须可供调试。避免无边界的「魅力+100」及单一概率按钮吞没人格。玩家在界面上读到的是行为、语言、共同经历与来自可信来源的判断。保留作弊/开发调试模式查看状态以便排查，而正式玩家体验要对人物保持尊重与未知性。

## 9. 文档与开发日志规则

每次设计或代码迭代必须留下：变更日期、版本、修改文件、完成的真实内容、仍未完成的内容、自动/人工测试结果、已知问题、下步工作；变更涉及统一接口或人物关系规则时，必须同步调整对应文档。不得以「方案已写」冒充「功能已运行」。

推荐将程序架构决策保存在 `docs/adr/`，核心模型放 `docs/model/`，UI规范放 `docs/ui/`，剧情生成规则放 `docs/narrative/`，世界模拟基准放 `tests/world/`。这些目录均为建议，**当前尚未在新仓库创建**。

## 10. 下一步真实开发任务（完成顺序）

1. 建独立仓库和最小启动工程，放入本套文档并启用自动测试；需用户明确指定或授权仓库目的地后再远程提交。
2. 实现可复现的世界时钟、种子、唯一ID、位置/房间连接、钱包/物品事务和事件账本。
3. 做一个能在手机浏览器操作的县城互动原型：进入房间、查看对象、地图寻路、事件筛选、存档读取。
4. 实现20名真正有日程、住处、职业、库存变化的重点NPC，并在外围挂载其余人口档案与区域批量模拟。
5. 做双向关系图＋关键记忆事件＋拒绝/同意门禁，再扩展婚姻、监护、继承、地方制度。
6. 接入县衙财政与宗门旅行两条真实系统链，验证跨系统状态一致。
7. 连续运行至少一个完整游戏年，对照不变量报告修复后再扩大。
